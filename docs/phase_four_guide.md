# 第四阶段：从“跑出一个分数”到可复现评测

第四阶段先冻结第三阶段的判定代码，整理输入、预测、评分和证据记录。不会看了 SciFact 答案后改规则，再把同一批数据的成绩当作泛化能力。

## 1. 先分清三个问题

| 问题 | 当前证据 |
| --- | --- |
| 程序是否按设计工作？ | 单元测试、50 条开发回归、实际 CLI/MCP 离线验证 |
| 规则在公开科学文本中发出什么提示？ | SciFact dev 全部所引文献配对的原生状态诊断 |
| 项目是否能完整审对任意论文？ | 目前没有足够证据；解析、检索、在线覆盖和科学判断都需要各自验证 |

不要把三者相加计算“综合准确率”。也不要把一千条刚写入数据库的记录全部查回来，描述成外部撤稿识别准确率。

## 2. 四步流程

```text
官方 archive + 固定 SHA-256
    └─ prepare：构建全部配对，保存输入/金标/版本清单
         ├─ inputs.jsonl ── run：只预测，逐条保存状态/原文/错误
         └─ gold.jsonl ──── score：预测完成后才读答案，计算指标
                                  └─ compare：相同数据上的重跑或对照
```

这里的“金标”只是数据集提供的标注答案。代码用 `InputCase` 和 `GoldCase` 两个模型隔开，前者禁止额外字段。`make_predictor()` 返回的函数只接收 `InputCase`，不会拿到标签或标注证据句索引。

数据准备使用 `cited_doc_ids` 中的每篇文献。比如一条论断引用 A、B，只有 A 被标为支持，B 也必须保留为该配对上的 NEI。旧流程在有支持/反驳证据时只遍历 evidence，因而漏掉 17 对；新流程为 300 条论断、340 对，不能与旧 323 对直接比较百分比。

## 3. 为什么分数不叫“准确率”

项目输出 TEXT_ALIGNED、POTENTIAL_CONFLICT、REVIEW_REQUIRED、INSUFFICIENT_EVIDENCE；SciFact 标注 SUPPORT、CONTRADICT、NEI。这两套标签回答的问题不同。

例如两条原文有矛盾，而规则都要求复核。这不是成功识别了两个矛盾，也不能算成“两个都判断错误”。报告会显示复核状态，同时矛盾**具体告警召回率为 0/2**。

再比如发出两个具体冲突告警，其中一个 gold=CONTRADICT，另一个 gold=SUPPORT，则告警查准率是 1/2。如果总共有四个矛盾配对，召回率就是 1/4。复核、证据不足和运行错误都仍留在召回分母。没有任何告警时查准率为 null，不能写成 100%。

`state_by_gold` 表能直接看到每类标注对应了多少种状态。`aligned_support_fraction` 检查文字相符是否经常落在支持标签上，但生产系统的 TEXT_ALIGNED 仍然要求人工阅读。REVIEW_REQUIRED 的比例只是状态频率，没有测量人的复核工时。

主摘录与标注证据句的重叠单独统计。一小段文字落在某个证据句内，只能计为 any-hit；只有完整包含一组证据句，才计为 complete-hit。两者都不是官方 SciFact 检索与证据评分。

## 4. 推荐读代码的顺序

| 文件 | 应该学会什么 |
| --- | --- |
| `benchmarks/schema.py` | 输入、答案、预测的字段分别属于谁；禁止额外标签进入输入 |
| `benchmarks/datasets.py` | 固定下载版本；只读 archive 指定成员；检查重复 ID、缺文献和冲突标签 |
| `benchmarks/predictors.py` | 现有规则如何接入统一输入；两个简单对照如何获得相同信息 |
| `benchmarks/metrics.py` | 从手算分子分母写成纯计算；异常不能从样本中消失 |
| `benchmarks/runner.py` | 每条落盘、中断留痕、环境/代码哈希、评分前后检查数据未变 |
| `benchmarks/reporting.py` | 将已有结果导出成完整表格和失败清单，避免展示层另作判断 |
| `benchmarks/__main__.py` | 用少量 argparse 代码连接准备、运行、评分、比较 |

对应测试是 `tests/test_evaluation_data.py`、`test_evaluation_metrics.py`、`test_evaluation_workflow.py`、`test_evaluation_legacy.py`。先读有手算答案的测试，再读实现，更容易理解为什么要保留这些检查。

## 5. 自己复现

完整命令见 [benchmark README](../benchmarks/README.md)。运行成功后先打开 `summary.md`，再用 `cases.tsv` 找到具体 ID，最后看 `failures.json` 的论断、完整摘要、所选原句和提示。

想检查计分是否可靠，运行 `score`。这个命令不会再调用判定器，只读取已保存的预测并核对指标。想检查预测是否稳定，再运行一次 `run`，使用新目录，然后 `compare`。耗时通常不同，所以语义输出哈希不包含耗时；原始逐条耗时仍保留在预测文件中。

每次运行都保留代码、数据、配置和环境。Git 提交号无法描述尚未提交的改动，因此还记录源文件哈希和工作区状态。代码哈希规范化换行符，让相同 Git 源码在 Windows/Unix 下可比较。`replay_verified` 要求数据、代码、配置、环境、逐条输出一致且两次均完整成功。

不要复用输出目录或覆盖失败记录。运行出错时先看 manifest；`incomplete` 表示未完成，不能冒充完整评测。单条 ERROR 会继续保留整批分母，最终命令仍返回失败状态。

## 6. 如何解释实际结果

当前测量的是**离线规则模式、给定所引文献完整摘要**的行为。它不使用嵌入模型或 LLM，不调用在线元数据 API，不要求从整个文献库找文章。SciFact dev 以前已经出现在本项目历史评测中，不能称为完全未接触过的测试集。

结果无论好坏都按固定协议保存。先判断主要问题是找不到对应原句、范围检查过于保守，还是具体数字/否定规则漏掉了表达；然后再为下一阶段设计新的开发数据和独立评估。不要用评测中挑出的失败例修规则后，继续宣称当前数据仍是独立测试。
